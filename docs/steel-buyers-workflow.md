# Steel Buyers workflow

The production project is `awqfpnzqwfjrjefoktgd`. No schema migration is required.

The module uses the existing static Home/Representation tokens in `pristeel-spie-standard.css`. All operational targets and unaccepted discovery companies open an accessible detail, including missing-contact companies. Filters distinguish a draft from a sent message. Page navigation reuses loaded data; it performs no contact research.

The existing `pppp-steel-buyer-discovery-daily` job remains the scheduler. Its worker researches at most six companies per run and four official pages per company. It checks canonical contacts and cross-module outbound history first, preserves existing `eu:*` source keys and checks company/domain identity. Procurement contacts rank before management and public mailboxes. Only published emails are stored; names require an explicit structured Person record owning the email. Missing contacts and failed research use a 30-day retry policy recorded in the existing run log. Conflicting identities remain for review. No paid enrichment provider is used.

Enrichment is appended as approved `dach_steel_target` commands to the existing command sheet, with the user authorization of 2026-10-06. It does not directly mutate business tables. Pending and failed commands are not replayed. A later run verifies the receipt and reads back the returned target. Existing command-sheet IDs also prevent duplicate pending appends.

The daily worker prepares at most two drafts for already-qualified targets with canonical contact identity. It invokes the existing authenticated draft generator, which checks canonical contact intelligence, cross-module guards, suppression, Gmail Sent history and exact threads before drafting. Existing live drafts are reused. Returned queue records are read back, and `approved_for_send=false`, `human_send_required=true` and absence of Sent evidence are required. A missing recipient never generates a draft. The workflow has no send endpoint; replies and project promotion keep their existing human gates.

The live bridge has no email-template write action/service. The minimal approved fallback is the single versioned module `supabase/functions/pppp-dach-steel-draft-generator/buyer-outreach.mjs`, containing `buyer_outreach_en` and `buyer_outreach_de`. The generator imports it; the UI contains no mail-merge copy. DE/AT/CH use German; all other markets use English, as requested on 2026-10-06. Profile variants choose approved prose and never print raw internal labels. Gmail sendAs HTML signature is preferred, preserving hosted logo URLs. The existing canonical signature mechanism is the fallback. HTML and plain text are generated together with one signature.

Verification: the scoped workflow tests exercise UI state and navigation, no-contact details, EN/DE personalization, Unicode/HTML escaping, actual MIME generation, signature selection, existing-draft reuse, Sent/reply guards, bridge append, stale retry and read-back. Gmail and database test adapters are simulated; they do not send email or mutate production data. An authenticated production browser session is needed to validate an actual new Gmail draft and the final visual layout.
